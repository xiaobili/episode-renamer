## A. 线上契约（前后端、或跨计划的两处必须逐字一致）

- **R2**　`_with_tmdb_titles` 从二元组改为三元组（向上暴露 `EpisodeMatch`），跨计划签名破坏是**有意接受**的：
  NFO 的内容来源必须是同一份解析结果，重新查 TMDB 会引入第二次外部调用与不一致。
  **判错代价**：漏改某个调用点会立刻 `ValueError`（响亮，不静默）。理由出自 **R59**（合并进来的 `title`
  在下游与用户手打的标题**不可区分**，故必须向上暴露 `EpisodeMatch` 而非重新推导）。
  锚点：`backend/app/api/renamer.py:_with_tmdb_titles`。
- **R59**　跨计划交接（计划 2 的设计交办）：**向上暴露 `EpisodeMatch`，不得让 NFO 从 `overrides` 反推标题** ——
  合并进来的 TMDB `title` 在下游与用户手打的标题不可区分。**判错代价**：NFO 用错标题来源，
  表现为「NFO 里的标题与文件名不一致」，静默且难查。（R2 是它的实现形态。）
- **R27**　两处接口面清理：路由 400 的 detail 改为 `str(exc)`（原写法产出重复前缀「TMDB API Key 无效: TMDB API Key 无效」，
  有精确等值断言钉住），以及删除 `_tmdb_summary` 的**死字段** `episode_title`（预览响应用不到它）。
  **判错代价**：用户读到重复文案；死字段继续留在线上响应里。
- **R5**　预览的 `nfo_scope` 在「启用了 NFO 但未配 TMDB」时报 `disabled`（而非 `episode_only`）——
  原写法让 `all(...)` 在空字典上返回 False。**判错代价**：用户看到一个含糊的状态标签，不致命。
  锚点：`frontend/src/components/FileTable.vue:NFO_SCOPE_HINTS`、spec §11。
- **R22**　六个 `tmdb_status` 字面串是**线上契约**（前端据以分支），必须有测试钉住**字面值**，
  否则把 `STATUS_MATCHED = "unavailable"` 之类互换可以全绿。**判错代价**：前端分支静默错位。
  锚点：`backend/tests/test_rename_routes.py:test_tmdb_status_literals_are_the_wire_contract`。
- **R34**　`/api/tmdb/test` 的真实状态集合有**第五个** `disabled`（服务端 `tmdb_enabled=false`）——
  计划的 Interfaces 只列了四个，代码是对的（设置页的文案表已为 `disabled` 单列一条）。
  **判错代价**：按计划的清单实现的人会漏掉这个分支 —— 该状态的产品价值就是给出可读诊断。
- **R66**　NFO 产物声明 `UTF-8` 但返回 `str`，故 Task 2/3 必须以 `encoding="utf-8"` 写盘。
  **判错代价**：中文标题 mojibake 或抛错（仅在非 UTF-8 locale 下暴露，见 R75）。
  锚点：`backend/app/core/nfo_writer.py:write_nfo_files`。
- **R74**　`nfo_matches` 用严格注解 `Optional[dict[str, EpisodeMatch]]` 而非 `dict | None`。
  **判错代价**：退化的注解削弱 Interfaces 的契约价值（无运行时成本，注解是字符串）。
- **R79**　预览行的 NFO 键名定为 **`tvshow`**（计划的 Interfaces 行与 spec §11 曾写 `"show"`）。
  **判错代价**：前端 `NFO_SCOPE_HINTS` 取不到键（依赖 R22 那类字面值测试的思路）。

## B. 后端行为 —— TMDB 降级、总开关与配置

- **R1**　缓存 TTL 由 `settings.tmdb_cache_ttl` 决定（`tmdb_resolver` 先写字面量 `3600`、Task 3 再接线，
  两步是**有意保留**的：客户端与解析器的任务不该顺手改全局配置）。**判错代价**：TTL 无视 `.env` 配置 ——
  影响仅为缓存时长，不致命，且那行改动在 diff 里显眼。锚点：`backend/app/core/tmdb_resolver.py:_DEFAULT_CACHE`。
- **R10**　「2xx 但 body 是 HTML」（代理 / captive portal）必须降级为 `unavailable`，**不得**以未分类异常 500。
  这是 R21 的起点。**判错代价**：整个预览请求 500，直接违反铁律。
- **R21**　在 `TmdbResolver._guarded`（外部数据边界）宽捕获未分类异常转 `TmdbUnavailableError`，
  同时**推翻 R13/R14 的 park**。理由：铁律措辞是「**绝不**阻断」，是分类性的而非枚举性的。
  **判错代价**：我们自己的编程错误（如 `TypeError`）会被降级而非暴露为 500 —— 有意的权衡，写进了 docstring。
  锚点：`backend/app/core/tmdb_resolver.py:_guarded`。
- **R23**　宽捕获**不得**压平已分类的 `TmdbNotFoundError`（我的原措辞「除 AuthError 外任何异常」不准）——
  六态降级靠它区分 `season_not_found` 与 `unavailable`。**判错代价**：「没这一季」显示成「TMDB 挂了」，
  用户去查网络而不是核对季号。锚点：`tmdb_resolver.py:_guarded` 的子句顺序。
- **R37**　`TmdbNotFoundError` 无人接会让 `/api/tmdb/test` 与 resolver 的 search 路径吐 500 —— **两处都修**。
  这条同时**证伪了 R24 的 park 依据**：制造者是拦截式代理 / DNS 屏蔽（中间设备），而我在 R10 已经接受过
  同一类制造者，却在这里拒绝，**不一致**。**判错代价**：各多 1 行生产代码与 1 条测试。
- **R39**　resolver 的 search 路径 404 → `STATUS_UNAVAILABLE`，**故意不与 detail 路径对称**
  （`/search/tv` 对不存在的剧回 200 + 空结果，故它的 404 只可能来自基础设施）。注释里写明理由，
  以免后来者「修」回对称。**判错代价**：诊断把网络问题说成剧名问题。锚点：`tmdb_resolver.py` 的 search 分支注释。
- **R49**　三条必修（全部源自计划）：(1) 空白 Key（`''`）不得短路 `.env` 回退 —— 两处优先级判定收敛到
  `build_tmdb_client` 单点，判定用**真值**而 `_pad_from_request` 用 `is not None`（语义不同，docstring 写明）；
  (2) `settingsStore.tmdb.enabled` 从死设置变成真开关（后端此前**没有** `enabled` 请求字段，属补完 spec）；
  (3) TMDB 设置变更必须刷新预览列。**判错代价**：设置页在说谎、Docker 主用例被破坏。
  锚点：`backend/app/api/tmdb.py:build_tmdb_client`、
  `backend/tests/test_tmdb_routes.py:test_build_tmdb_client_is_the_single_decision_point`。
- **R51**　`/api/tmdb/search` 也受服务端 `settings.tmdb_enabled` 约束（此前填了 Key 就照查不误）。
  **判错代价**：服务端关掉 TMDB 却仍允许搜索 —— 但那个「照查」正是缺陷。
- **R25**　单元套件**不得依赖外网**：真的会出网的用例改为 monkeypatch（不加 `network` marker、
  不给生产代码塞测试注入口）。真 Key 打真 TMDB 的端到端验证移到 `deferred-to-human`。
  **判错代价**：失去一条自动断言（其价值已由 Task 1 的 MockTransport 用例承担）。
- **R31**　`backend/tests/conftest.py` 用 autouse fixture 钉死配置 —— `Settings` 带 `env_file=".env"`，
  而 `.env` 是本设计支持的配置来源，故任何配了 Key 的机器上三条用例会真的出网。
  **判错代价**：实测在**有网**下这个洞会让 13 条红、污染整个套件（不只是那三条）。
  锚点：`backend/tests/conftest.py`。

## C. 后端行为 —— NFO 内容、落点与重命名集成

- **R63**　NFO 内容规范：**仅含空白的值也省略标签**（不只是空串）——理由是空标签会被部分刮削器
  当成「该字段为空」的真值而覆盖已有数据。**判错代价**：中间隔一层空白的值直接写坏用户的数据。
  锚点：`nfo_writer.py:_text`。
- **R67**　决策顺序是**契约**：三桶拼接（每集 → 剧集级 `tvshow` → 季级 `season`），
  且拒绝文案必须含子串「多部剧」。**判错代价**：单剧时两种顺序重合，**只有多剧才暴露**；
  文案不符会让前端断言与 docstring 三方不一致。锚点：`nfo_writer.py:build_nfo_decisions`。
- **R70**　决策的 `file_id` 归属按**已排序**顺序确定（原随输入顺序变化）；确定性断言加强到同时比较
  `file_id` 与 `kind`（原注释声称「逐项一致」却只比 `.path` —— 注释比断言强）。**判错代价**：无。
- **R71**　混放守卫从「同目录」扩到「**root 之下任意层级存在别剧的文件就拒绝**」。
  理由：拒绝是安全方向（最坏是古怪布局下少写剧集级 NFO，且预览列可见），另一边是不可逆的库污染。
  **判错代价**：某个没想到的布局会少写剧集级 NFO —— 可见、可纠正。锚点：`nfo_writer.py` 的混放校验。
- **R73**　**单季布局下剧集根必须上溯一层**：`common_parent` 只给一个季文件夹时，`tvshow.nfo` 会落进
  `Season 02/`，而 Emby/Jellyfin 只在剧集根找它 —— **等于白写**。判据**复用** `parser._SEASON_DIR_PATTERNS`，
  不另立正则；上溯单步、非循环。**根因是 spec §9.3 不完备（举例不覆盖规则）**，已同步修正 spec。
  **判错代价**：上溯过头会把 `tvshow.nfo` 写到剧集根之上（见 R76）。锚点：`nfo_writer.py:_show_root`、
  `tests/test_nfo_plan.py:test_single_season_folder_still_puts_tvshow_at_the_show_root`。
- **R76**　`_show_root` 在**剧目录本身就叫季名**时上溯过头，把 `tvshow.nfo` 写到库根。
  **裁定：只做文档补救，不改代码**——审查者证明了**不存在纯路径的修法**（`show_name == basename(root)`
  在好/坏两种布局下相等；要判就得探测文件系统，破坏「纯函数、不碰 FS」契约）。
  **判错代价**：该组合下污染库根 —— 但 dry-run 清单在执行前显示落点，可见、可纠正。已写进 spec §9.3。
- **R77**　`rename_dup`（「自动编号」）下每集 NFO 必须跟随**解析后的真实目标**（`X_1.mkv` → `X_1.nfo`），
  否则视频拿不到配对 NFO，且覆盖模式下会改写**冲突那一集**的文件。**判错代价**：错配（非静默，会进 `nfo_skipped`）。
  锚点：`local_renamer.py` 重命名循环里的 `nfo_path_by_file` 改指向。
- **R78**　`nfo_scope` 的 `full` 判据改为**按剧**（逐文件 `all()` 建立在只挂首个 `file_id` 的组级决策上，
  故同一部剧选两集这个**正常情形**会把 `full` 误报成 `episode_only`）。这是「`all()` 建在空/不完整集合上」
  这一形态的第 4 次，也是最严重的一次。**判错代价**：用户看到「仅每集 NFO」而实际写了全套。
  锚点：`backend/app/api/renamer.py` 的 `nfo_scope` 计算。
- **R82**　NFO 管线**只处理视频**，判据用 `FileInfo.is_subtitle`（扫描器已设，比嗅探扩展名精确，
  不会与 `settings.subtitle_extensions` 漂移），两处 `NfoEntry` 构造点都过滤，**不影响字幕重命名**。
  **判错代价**：每个字幕旁多写一个无意义 `.nfo`（纯库污染），且决策按路径排序时会挂到字幕行上。
  spec §9.1 的对应条款在提交 `384801f` 里被标为 **R80** —— 而**两份 ledger 都没有 R80 的正文**
  （见 H 节），本条是它唯一的实质记录。
- **R83**　只有字幕的目录会报 `episode_only` 而实际零落点。**裁定：defer** —— 把 `all(...)` 换成过滤后的
  视频列表会踩到**空列表恒 True**的老坑（变成 `full`，比现在更假）；修对需要第五个 scope 取值或回落规则，
  那是线上契约变更。**判错代价**：每行 `nfo=null`、状态标签含糊（UI 后果轻）。锚点：同 R78 的位置。
- **R86-1**　**没落地的行不写 NFO**（`skip` / `abort` / 冲突行）。最终审查者复现了两例，`abort` 那例最糟：
  用户选了最保守策略、被告知该行**没有落点**，然后在库里发现新文件躺在别人的视频旁。
  **判错代价**：静默写错元数据 —— 本程最严重的一类。锚点：`local_renamer.py` 的 `dead_file_ids` / `_keep_decision`。
- **R86-2**　**§9.4 的可见性安全阀必须真的交付**：结果对话框要列**落点路径**（不只计数与原因），
  预览与结果都要能看见 NFO 落到哪里。**这条要紧在**：R76/R77 接受「上溯过头」这个已知类别的理由
  正是「dry-run 清单会在执行前把落点显示出来」—— 而修复前那个前提**在实现上是假的**。
  **判错代价**：所有「可见、可纠正」的兜底论证一起失效。锚点：`frontend/src/components/ResultDialog.vue`。
- **R87**　「**没有任何东西落地 → 剧集级文件也不写**」。**裁定：接受** —— 安全方向（不写元数据比写错好），
  已文档化。**判错代价**：某个古怪场景下少写一个剧集级 NFO —— 可见（预览/结果都列落点）、可纠正。
- **R88**　**§9.1.1 既有同前缀 NFO 跟随改名**（用户报告的需求；`.nfo` 从不进扫描、不在批次里，
  是**我设计的真空**）。四条边界：只对视频、只跟同前缀那一个（绝不碰 `tvshow`/`season.nfo`）、
  **与是否生成 NFO 无关**、**先移动后生成**（使「生成开 + 覆盖关」保留用户原有内容）。失败处理沿用铁律：
  目标已存在**不覆盖**（宁可留下可见的孤儿也不静默改写别人的元数据）、移动失败不阻断批量、dry-run 不移动但列出。
  OpenList 不在本期。**判错代价**：用户报的原症状回归。锚点：`local_renamer.py:carry_same_stem_nfo`、spec §9.1.1。

## D. 前端行为（用户可见）

- **R43**　`apiKey` 与 `language` 一致地 `.trim()`（从 TMDB 网页复制的 Key **经常带尾部空白或换行**，
  否则 401 →「API Key 无效」→ 用户查不出原因）。**判错代价**：误导性诊断，正是本程一直在修的那一类。
  锚点：`frontend/src/stores/settingsSchema.js`。

## E.（附录）验证、密闭性与覆盖 —— 什么被守着、什么没有

**收录理由**：这些裁定不改变产品行为，但决定「合并后哪些东西一改就没人拦」。
分类规则把它们排除在实体之外，单列于此。

- **R29**　execute / dry-run 路径的标题合并**必须有覆盖**（原仅一次性脚本验证）：
  两行若被删掉或漏传，**没有任何测试会红**，用户会看到预览有标题、执行后文件名里没有。
  锚点：`tests/test_rename_routes.py` 的相关用例（变异：`overrides=effective_overrides` → `req.overrides` 必须红）。
- **R32**　`tmdb_overrides` 的接线覆盖（唯一发送用例跑在 `disabled` 路径上，`TmdbResolver` 根本不被构造，
  故删掉那一处传递 82 条全绿）—— 它是「预览表可重选」这个能力的**唯一承载**，静默失效时用户点了重选毫无反应。
- **R9**　`get_tv_detail` 是三个客户端方法里唯一没有直接测试覆盖的一个（`TmdbShow` 的字段映射），
  而 resolver 与 NFO 都依赖它的返回值 —— **判定为真实缺口，责任在计划**，在修复轮补一个映射测试。
  **判错代价**：字段映射若错，要到写 NFO 时才以「剧集元数据不对」的形式暴露，定位成本更高。
- **R15**　计划写的测试文件**不可能达到 23 passed**：6 个用例省略 `cache=` 而共用模块级 `_DEFAULT_CACHE`，
  键必然碰撞，断言落在陈旧值上（实测 GREEN 阶段 6 failed）。实施者用 autouse fixture 每用例清缓存修复 ——
  **这是计划里的测试隔离缺陷**。**判错代价**：每用例清缓存会重置生产缓存，但「缓存跨 resolver 实例存活」
  这一属性仍由专用用例（显式传 `cache=`）守护。
- **R16 / R26**　「零鉴别力的测试」这一形态的**前两次**（都是计划写的）：R16 的并发合并不让出控制权
  （**删掉缓存锁该测试依然通过**，而它是 spec §6.3「同键并发合并为一次外部调用」的唯一守护者）；
  R26 的 4 条标题用例在「退回单遍解析」与「无条件覆盖」两种坏实现下**全绿**。
  两次都要求变异验证（去锁 → 必须 FAILED）。**这两条是 R30 的由来。**
- **R28**　「`401 → TmdbAuthError` 只由 Task 1 保证、两条用例之间是约定而非编译期约束」——**裁定：不是缺口**。
  链路两端各由一个测试钉住（Task 1 钉「401 → AuthError」，Task 3 钉「AuthError → 400」），缺一即红。
  **判错代价**：语义级改动（如把 403 也映射成 AuthError）两端都不红 —— 无人会做的改动，且不在设计范围内。
- **R30**　**流程改进但产出可量化**：从 Task 4 起每次派发显式要求实施者报告「哪条指定测试在把实现改坏后仍通过」
  并要求变异验证。「零鉴别力的测试」此前出现三次且**三次都是计划写的**；R30 生效后
  计划 2 的首个任务一次达成「16 个变异、零孤儿测试」（计划 1 同位置需要一轮修复）。
- **R35 / R38 / R41**　`/api/tmdb/test` 四分支与 `/search` 行为补测（该端点存在的全部意义就是告诉用户 Key 能不能用）；
  空查询用例的密闭性改为**无条件**（打桩），原写法删掉守卫后**真的出网**且真 TMDB 回 401 会让断言**照样满足**
  —— 即它在联网环境下本是零鉴别力的。
- **R44 / R62**　前端三条接线的**补偿措施**：`stores/settings.js` 的接线零自动化覆盖（断言脚本加载不了它），

  **判错代价**：这些分支若被将来的重构弄坏，只有人工走查能发现 —— 本项目已知且被接受的缺口。
